# Frontend. Руководство по разработке и оформлению кода

Технологический стек и обоснование выбора — [`decisions/01-tech-stack.md`](decisions/01-tech-stack.md). Здесь — конкретные конвенции кода для `src/renderer/`.


## Архитектура

Архитектура приложения — FSD (Feature-Sliced Design) с высоким уровнем декомпозиции на компоненты: одна логическая/визуальная единица — новый компонент. Код стремится к **низкой связанности и высокому зацеплению (low coupling & high cohesion)**.

Слои (сверху вниз — верхний может импортировать только из нижних, никогда наоборот):

| Слой | Алиас | Назначение |
|---|---|---|
| `app` | `@/app` | Инициализация приложения: провайдеры (`ThemeProvider`), роутинг (`Router`), глобальные стили |
| `pages` | `@/pages` | Экраны — композиция виджетов/фич/сущностей под конкретный route. Собственной бизнес-логики почти не содержат |
| `widgets` | `@/widgets` | Крупные самостоятельные блоки UI, собранные из нескольких фич/сущностей (например, канбан-доска целиком) |
| `features` | `@/features` | Одно пользовательское действие с бизнес-ценностью (например, логин, перенос задачи между колонками) |
| `entities` | `@/entities` | Бизнес-сущности домена (Задача, Проект, Лейбл) — их UI-представление и модель на фронтенде |
| `shared` | `@/shared` | Переиспользуемый код без привязки к бизнес-логике: UI-кит, утилиты, типы |

Пока в проекте реально используются `app`, `pages` и `widgets` (первый виджет — `widgets/sidebar`, сайдбар авторизованного приложения); `features`/`entities` появятся вместе с канбан-доской и остальными фичами — заводи слой только когда для него есть код, не создавай пустые директории впрок.

Внутри слайса — сегменты `ui/` (компоненты), `model/` (состояние, бизнес-логика, схемы валидации) и `api/` (функции поверх `window.api.*` и хуки TanStack Query, которые их вызывают) уже используются в проекте. Другие стандартные FSD-сегменты (`lib/`, `hooks/`, `config/`) пока не добавлены — заводи их по мере необходимости, когда для них появляется код, а не заранее «про запас».

Наружу слайс отдаёт **публичный API** — barrel-файл `index.ts`, реэкспортирующий только то, что нужно снаружи:

```ts
// pages/login/index.tsx
export { LoginPage } from "./ui/LoginPage";
```

Импорт мимо `index.ts` в чужой слайс — нарушение границы слоя.

Архитектура также следует принципу **DRY**: дублирование компонентов решается через декомпозицию и рефакторинг, а не копипастой.


## Naming и структура компонента

- Компоненты — `PascalCase.tsx`, один компонент на файл, имя файла = имя компонента
- Типизация функционального компонента — через `FC` из `react`:
  ```ts
  export const LoginForm: FC = () => {...};
  export const ThemeProvider: FC<PropsWithChildren> = ({ children }) => {...};
  ```
- Пропсы компонента и любые другие типы во фронтенде — через `type`, не `interface`:
  ```ts
  type UserCardProps = {
    fullName: string;
    email: string;
  };
  ```
  `interface` в проекте зарезервирован за бэкендом — только там, где он реализуется классом (`implements` в `src/main`, см. [`BACKEND_CODE_STYLE_GUIDE.md`](BACKEND_CODE_STYLE_GUIDE.md)); во фронтенде классов с `implements` нет, поэтому `interface` там не используется вовсе
- Избегай inline типов: максимум 2 поля для inline типа, если больше - выноси в отдельный тип 
- Экспорты — именованные (`export const X`), не `default`; наружу слайса — через `index.ts`
- `api/*.ts` — всё, что вызывает `window.api.*`, и хуки TanStack Query/Mutation, построенные поверх этих вызовов (`useTasksQuery`, `useChangeTaskStatusMutation`). Компонент из `ui/` не обращается к `window.api` напрямую, а идёт через хук/функцию из `api/`. **Один файл — одна функция/хук, имя файла = имя экспорта** (по аналогии с компонентами из `ui/`), а не общий `tasks.ts`/`auth.ts` на весь сегмент:
  ```ts
  // api/loginWithAccessToken.ts
  export const loginWithAccessToken = (accessToken: string): Promise<LoginResult> =>
    window.api.auth.login(accessToken);

  // api/useTasksQuery.ts
  export const useTasksQuery = () => useInfiniteQuery({ ... });
  ```
- `model/*.ts` — не-UI логика сегмента, которая не ходит в IPC: Zod-схемы, локальное состояние (`viewMode.ts`), вычисления. Схема валидации формы — в `model/`, даже если рядом в `api/` лежит функция, которая эту форму отправляет: `api/` — это только про `window.api`, а не про всё, что не UI
- Импорты между слоями — только через алиасы `@/app`, `@/pages`, `@/widgets`, `@/features`, `@/entities`, `@/shared`, `@/main` (типы бэкенда из `src/main/*/index.ts`); внутри слайса — относительные (`./GetTokenSteps`)


## Язык кода и интерфейса

- Код — на английском: имена, комментарии, тесты, ключи и служебные строки
- Тексты, которые видит пользователь (подписи, кнопки, ошибки форм, уведомления), — **тоже на английском**; они живут в JSX-компонентах, отдельного словаря локализации в проекте нет. Русский язык используется только в документации (`docs/`, `README.md`, `CLAUDE.md`), но не в интерфейсе
- Техническое `message` из IPC-ответа не показывается пользователю как есть: сопоставь тип ошибки (`error.type`) с собственной формулировкой на стороне фронтенда
- Подписи, приведённые в [`SPECIFICATION.md`](SPECIFICATION.md) по-русски («Новая задача», **Показать все**, «ещё N»), задают **смысл** элемента, а не строку для вставки в JSX — переводи их на английский при реализации


## Роутинг

Роутинг собран в `app/Router.tsx` на `createHashRouter` (именно hash-роутер: в production renderer открывается через `file://`, где history-роутинг не работает).

Там два раздельных роутера — `authRouter` (экран входа) и `appRouter` (основное приложение, обёрнутое в `AppLayout`) — и `Router` выбирает между ними по состоянию сессии из `useSession()` (`app/SessionContext.tsx`):

- `status === "loading"` — сессия ещё не проверена (идёт `auth:checkSession` при монтировании `SessionProvider`) → показывается `Loader` по центру экрана, ни один из роутеров не рендерится
- `status === "authenticated"` → `appRouter`
- `status === "unauthenticated"` → `authRouter` (если сохранённый токен оказался невалиден, `session.errorMessage` — сообщение из бэкенда — показывается на экране входа)

`SessionContext` — единственный источник состояния авторизации на фронтенде, поднят в `app/` через React-контекст (см. «Загрузка данных и состояние»): `authenticate(user)` переводит в `authenticated` сразу после успешного логина (без повторного запроса), `logout()` дёргает `auth:logout` и возвращает в `unauthenticated`.

`appRouter` — не плоский список страниц, а один layout-роут: `AppLayout` (Mantine `AppShell`) рендерит `widgets/sidebar` в `AppShell.Navbar` и `<Outlet />` в `AppShell.Main`, туда как дочерние роуты подключаются экраны авторизованного приложения. `authRouter` — плоский, без общего layout (экран входа сайдбар не показывает).

Чтобы добавить экран в авторизованную часть: слайс в `pages/<name>/` с `ui/<Name>Page.tsx` и barrel `index.ts` → запись в `children` `appRouter`-роута с `AppLayout` → импорт страницы через алиас `@/pages/<name>`. Для экрана вне авторизации (аналог `LoginPage`) — запись верхнего уровня в `authRouter`.


## Загрузка данных и состояние

Серверное состояние — **TanStack Query** (`@tanstack/react-query`, см. [`decisions/01-tech-stack.md`](decisions/01-tech-stack.md) и скилл `tanstack-query`). Глобального стора (Zustand, Redux) в проекте по-прежнему нет.

- Запрос к бэкенду — функция в `api/` слайса поверх `window.api.*`, оборачивается в `useQuery`/`useInfiniteQuery`/`useMutation` там же (не в компоненте `ui/`); `useState` остаётся для чисто локального UI-состояния (открыт ли модал, выбранный таб), не для серверных данных
- Курсорная пагинация Todoist (лимит 200) — `useInfiniteQuery` с `getNextPageParam` по `nextCursor` из контракта; страница «Задачи» — эталонная реализация (`pages/tasks/api/useTasksQuery.ts`)
- Query key, которым делятся несколько слайсов (например, список задач читается страницей и пишется фичей смены статуса), заводится в `entities/` и импортируется оттуда — не дублируется
- Оптимистичные обновления (`onMutate`/`setQueryData`/откат в `onError` или при `{ ok: false }`, раз IPC-результат — discriminated union, а не throw) — стандартный способ применять drag-and-drop и другие мгновенные UI-изменения, синхронизируемые с Todoist асинхронно
- Кэширования сверх того, что даёт TanStack Query по умолчанию, не делай без явного запроса — конкретно для Дашборда кэш заводить не нужно (см. `pages/dashboard`), пока экран не потребует переиспользования данных между виджетами
- Состояние, общее для нескольких слайсов и не являющееся серверными данными (сессия), — общий слой (`entities`/`app`) через React-контекст, как и раньше


## Mantine UI

- Компоновку и отступы делай через пропсы Mantine (`gap`, `p`, `radius`, `w`, `fullWidth` и т.д.), а не через `style={{...}}` — inline-стили оставляй только для того, что нельзя выразить пропсами (пример обоснованного случая — `display`/`minHeight` для центрирования блока на весь экран)
- За документацией и списком пропсов компонентов Mantine обращайся к MCP-серверу `mantine`, а не отвечай по памяти — API библиотеки меняется между мажорными версиями
- Цветовая тема и её переопределение — только в `app/ThemeProvider.tsx`, не создавай локальные `MantineProvider` за пределами тестов
- Иконки — пакет `lucide-animated` (обёртки над `lucide-react` с hover-анимацией через `motion`); импортируются точечно (`import { SearchIcon } from "lucide-animated"`), не через `lucide-react` напрямую


## Работа с формами и IPC

- Валидация форм — Zod-схема в `model/`, подключается через `schemaResolver` из `@mantine/form`:
  ```ts
  const form = useForm({
    initialValues: { accessToken: "" },
    validate: schemaResolver(authFormSchema, { sync: true }),
  });
  ```
- Схема для поля, определённого на бэкенде (например, `accessTokenSchema`), не дублируется на фронтенде — импортируется из `@/main/*`
- Вызовы бэкенда — только через `window.api.*` (IPC-мост из `preload`), и только обёрнутые в функцию `api/`-сегмента, а не напрямую из компонента
- Результат IPC-вызова — discriminated union, а не throw:
  ```ts
  type LoginResult =
    | { ok: true; user: AuthenticatedUser }
    | { ok: false; error: AuthError };
  ```
  Обрабатывается через `if (result.ok)`, ошибка показывается через `form.setFieldError` или `notifications.show`
- Побочные эффекты после успешной/неуспешной отправки — `notifications.show` из `@mantine/notifications`


## Рецепт: как добавить функциональность

Порядок шагов — снизу вверх по слоям FSD: сначала то, что переиспользуется, потом композиция.

### Новая фича или экран

1. Определи слой по смыслу: бизнес-сущность → `entities`, одно пользовательское действие → `features`, крупный самостоятельный блок из нескольких фич → `widgets`, экран под route → `pages`
2. Заведи слайс `<layer>/<name>/` с сегментами `ui/`, `model/` и `api/` — только теми, для которых реально есть код
3. `api/` — обёртки над `window.api.*` и хуки TanStack Query/Mutation поверх них; `model/` — остальная не-UI логика (Zod-схемы, вычисления, локальное состояние); типы результата IPC импортируй из `@/main/<module>`, свою копию не пиши
4. `ui/` — компоненты, один на файл, `FC`, декомпозиция до отдельной логической/визуальной единицы; пропсы Mantine вместо inline-стилей
5. `index.ts` — публичный API слайса: реэкспорт только того, что нужно снаружи
6. Подключи слайс сверху: в страницу, виджет или роутер (см. «Роутинг»)
7. `*.spec.tsx` рядом с компонентами на пользовательские сценарии, с моком `window.api`

### Правка существующего компонента

Если компонент разросся или логика повторяется — выдели подкомпонент или функцию в `model/`, а не копируй. Три похожих случая — повод для общего компонента в `shared/ui`, два — ещё нет.

### После изменений

Пройди SDLC (раздел ниже). Если добавился новый алиас — синхронизируй `tsconfig.web.json` и `vitest.config.ts` в одном коммите.


## Чего делать нельзя

- Обращаться к `window.api` напрямую из `ui/` или `model/` — только через функцию `api/`-сегмента
- Импортировать `@doist/todoist-sdk`, `electron` или что-либо из `src/main`, кроме типов и Zod-схем через `@/main/*`
- Импортировать из чужого слайса мимо его `index.ts` или из слоя выше по списку (`entities` не знает про `features`, `features` — про `widgets` и `pages`)
- Дублировать на фронтенде Zod-схему или тип, уже определённый в `domain/` бэкенда
- Создавать пустые слои и сегменты впрок
- Верстать отступы и размеры через `style={{...}}`, если это выражается пропсами Mantine
- Создавать `MantineProvider` за пределами `app/ThemeProvider.tsx` и тестов
- Искать элементы в тестах по `data-testid` вместо доступных пользователю признаков
- Использовать `interface` для пропсов компонента или любых других типов — только `type` (см. «Naming и структура компонента»)


## Тестирование

Обязательному покрытию unit-тестами подлежат UI-компоненты с функциональностью — формы и интерактивные виджеты (например, drag-and-drop канбан-доска в `widgets/task-board`), а также вынесенная из них логика (`lib/`-хелперы, кастомные хуки). Чисто презентационные компоненты без ветвлений и обработчиков (простой вывод пропсов) тестами можно не покрывать.

- Тест — `*.spec.tsx` (`*.spec.ts` для хелперов/хуков без JSX), лежит рядом с тестируемым файлом (не в отдельной `__tests__/`)
- `render`, `fireEvent`, `waitFor`, `within`, `userEvent`, `describe`/`it`/`expect`/`vi` — глобальны, импортировать не нужно (настроено в [`vitest.setup.ts`](../vitest.setup.ts)). Исключение — `screen`: импортируется явно из `@testing-library/react`, потому что коллизирует с DOM-глобалом `window.screen`
- Запросы к DOM — через доступные пользователю признаки (`getByRole`, `getByLabelText`, `findByText`), не через `data-testid` или детали реализации
- IPC-мост в тестах мокается через `Object.defineProperty(window, "api", ...)` в `beforeEach`
- Локальный `MantineProvider` в тесте — только дефолтный (`<MantineProvider>`), без кастомной темы, если тест не проверяет саму тему.
- Мокирование методов `windows.api.*` происходить в каждом spec-файле отдельно (и только те методы, что используются в тестируемом компоненте).
- `renderHook(() => useX(propValue))`, где `propValue` — литерал массива/объекта, создаёт новую ссылку на каждый рендер; если хук зависит от такого пропа в `useEffect`, это зацикливает ре-рендеры и вешает воркер Vitest (OOM). Выносите такие пропы в переменную перед `renderHook`, чтобы ссылка была стабильной, как в реальном родительском компоненте.


## Форматирование и импорты

Форматирование и линт — Biome (`yarn format`, `yarn lint`), конфиг в [`biome.json`](../biome.json). Ключевое, что нельзя авто-исправить редактированием руками мимо форматтера:

- Двойные кавычки, точки с запятой всегда, скобки у всех стрелочных функций (`(x) => x`, не `x => x`)
- Сортировка и группировка импортов — автоматическая (`organizeImports`), не выстраивай их руками
- Порядок алиасов в новых конфигах (`tsconfig.web.json`, `vitest.config.ts`) — `@/app`, `@/pages`, `@/widgets`, `@/features`, `@/entities`, `@/shared`, `@/main`; при добавлении нового алиаса синхронизируй оба файла в одном коммите


## SDLC

1. разработка новой фичи / внесение правок
2. добавление / актуализация unit-тестов
3. проверь, нет ли висящих ссылок / нужно ли обновить документацию / завести новый ADR (последнее согласуй со мной)
4. `yarn typecheck` & `yarn format`
5. `yarn test`
6. ожидание ревью от человека
7. `/git-commit`

Шаги 4 и 5 частично автоматизированы хуками Claude Code (`.claude/settings.json`): `yarn format` прогоняется по каждому изменённому файлу после правки, а `yarn typecheck` и `yarn test` — перед завершением работы агента, если менялось что-то в `src/`; при красном результате агент не заканчивает работу, а чинит. Хуки — страховка, а не замена шагам: запускай проверки и сам, не дожидаясь конца сессии.


## Claude Code

- Реализация фичи или правки на фронтенде — скилл `feature-frontend`; фича, затрагивающая и бэкенд, и фронтенд, — скилл `feature-fullstack`
- Документация и пропсы компонентов Mantine — MCP-сервер `mantine`, а не память
- Ревью готового дифа на соответствие этому руководству — агент `code-reviewer`
- Оформление коммита — скилл `git-commit`
