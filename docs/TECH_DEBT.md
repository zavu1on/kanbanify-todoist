# Технический долг

Реестр кода, который уже сейчас нарушает принятую конвенцию (в отличие от [`DEFERRED.md`](DEFERRED.md), где работа не сделана из-за отсутствующего функционала — здесь функционал есть, но написан не по правилам). Запись без конкретного файла и без объяснения, какую конвенцию она нарушает, бесполезна — такая заявка не тех.долг, а общая идея, ей тут не место.


## Как пользоваться

**При обнаружении** — заведи строку с указанием файла, нарушенной конвенции и опции исправления.

**При исправлении** — удали строку целиком, а не помечай как исправленную (история — в git).


## Реестр

| Код | Нарушение | Как исправить |
|---|---|---|
| [`UpdateTaskStatusUseCase`](../src/main/tasks/application/use-cases/UpdateTaskStatusUseCase.ts) | Обновление Kanban-статуса задачи идёт напрямую через `ITaskGateway.updateTaskStatus`, минуя доменную сущность `Task` — бизнес-правило (`KanbanStatus.resolve`/`applyTo`) не применяется к уже загруженной сущности перед сохранением, в отличие от принятого паттерна «сущность → метод → порт» (см. [`BACKEND_CODE_STYLE_GUIDE.md`](BACKEND_CODE_STYLE_GUIDE.md), раздел «Архитектура» — правило про бизнес-логику только в доменных сущностях, введённое при реализации CRUD проектов) | Загружать `Task` через порт (или мэпить уже полученную из `ListTasksUseCase` сущность), вызывать метод сущности, применяющий `KanbanStatus` к `labels` (например, `Task.changeStatus(status)`, использующий уже существующий `KanbanStatus.applyTo`), и сохранять результат через `ITaskGateway.save`/`upsert`, а не через специализированный `updateTaskStatus` |
| [`KanbanStatus`](../src/main/tasks/domain/value-objects/KanbanStatus.ts), [`Task`](../src/main/tasks/domain/entities/Task.ts) | Нарушают правила из [`BACKEND_CODE_STYLE_GUIDE.md`](BACKEND_CODE_STYLE_GUIDE.md) («Naming и структура кода», раздел про VO и сущности, введённый при реализации CRUD проектов): `KanbanStatus.resolve`/`applyTo` — бизнес-логика (разрешение конфликта лейблов) внутри VO, хотя VO бизнес-логику содержать не должен; `Task` — публичный конструктор с `readonly`-полями без фабрик `create`/`reconstitute` | Разрешение конфликта лейблов перенести в `Task` как метод сущности (например, `Task.resolveStatus()`, использующий `KanbanStatus` только как VO-обёртку над уровнем статуса, без `resolve`); `Task` — приватный конструктор + `create`/`reconstitute`. Делать вместе с рефакторингом `UpdateTaskStatusUseCase` выше — оба пункта трогают один и тот же код |
