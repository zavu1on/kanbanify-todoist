# 02. Конвенции архитектуры бекенда и фронтенда

**Дата:** 2026-08-03
**Автор:** mikhail
**Статус:** Принято
**Связанные решения:** [01-tech-stack.md](01-tech-stack.md), [03-ai-harness.md](03-ai-harness.md)


## Контекст

[Решение 01](01-tech-stack.md) выбрало парадигмы — чистую архитектуру для main-процесса и FSD для renderer'а — но не зафиксировало, как именно они разворачиваются в этом репозитории. Обе парадигмы допускают несовместимые между собой реализации, и выбор приходится делать в каждой из точек:

- нарезка верхнего уровня на бекенде: сначала слои (`domain/`, `application/`, `infrastructure/` в корне), а внутри модули — или сначала модули (`auth/`, `tasks/`), а слои внутри каждого
- где живёт тип, общий для main и renderer: в отдельном пакете общих типов, в `src/preload` или в доменном слое модуля-владельца
- как отказ пересекает границу IPC: исключением, которое Electron сериализует по своим правилам, или значением
- как собираются зависимости: DI-контейнером или вручную
- что модуль и слайс отдают наружу: любой файл по прямому пути или только явный публичный API

Первый модуль (`auth`) и первый слайс (`pages/login`) уже реализованы, дальше идут **Задачи**, **Календарь** и канбан-доска. Конвенции нужно зафиксировать сейчас, пока их не размножили по-разному в четырёх модулях: несогласованная структура — это то, что потом переписывается целиком, а не правится точечно.

Отдельный контекст — разработка ведётся преимущественно через AI-агента (см. [03-ai-harness.md](03-ai-harness.md)), который каждый раз начинает с пустым контекстом. Для него единообразие структуры важнее, чем для человека: агент воспроизводит то, что видит в соседнем модуле, поэтому первый прецедент становится нормой независимо от того, была ли она осознанной.


## Решение

Зафиксировать перечисленные ниже конвенции. Точные правила именования, оформления и пошаговые рецепты добавления функциональности вынесены в два руководства — [`BACKEND_CODE_STYLE_GUIDE.md`](../BACKEND_CODE_STYLE_GUIDE.md) и [`FRONTEND_CODE_STYLE_GUIDE.md`](../FRONTEND_CODE_STYLE_GUIDE.md); они, а не этот ADR, являются рабочим источником правды и обновляются по мере развития кода. Здесь — только сами решения и их обоснование.

**Бекенд** (`src/main/`, `src/preload/`):

- **Модуль — единица верхнего уровня.** В корне `src/main/` лежат модули по доменным областям (`auth/`, далее `tasks/` и т.д.), внутри каждого — три слоя: `domain/`, `application/`, `infrastructure/`. Общий для модулей код — в `src/main/shared/`
- **Правило зависимостей — только внутрь.** `infrastructure` → `application` → `domain`; `domain` не знает ни про Electron, ни про SDK. `infrastructure` реализует интерфейсы портов, объявленные в `application/ports/`
- **Стиль — ООП:** классы, а не наборы функций. Use-case — класс с методом `execute`, зависимости приходят через конструктор
- **IPC-контракт живёт в `domain/contracts/` модуля-владельца** и реэкспортируется через barrel-файл `<module>/index.ts`. `preload` и renderer импортируют его оттуда, своей копии не заводят
- **Ошибки не пересекают границу IPC как исключения.** IPC-контроллер всегда возвращает сериализуемый discriminated union вида `{ ok: true; ... } | { ok: false; error: { type; message } }`, отображая доменные ошибки в тип по `instanceof`
- **Value objects валидируются без исключений** — статическая фабрика `safeParse`, возвращающая union успеха и ошибки
- **DI — ручной, без фреймворка**, в единственной точке сборки `src/main/index.ts`
- **`src/preload` — только мост:** описание `contextBridge`/`ipcRenderer.invoke`, никакой бизнес-логики

**Фронтенд** (`src/renderer/src/`):

- **Слои FSD** — `app`, `pages`, `widgets`, `features`, `entities`, `shared`; импорт разрешён только сверху вниз. Каждому слою соответствует алиас (`@/pages`, ...), плюс `@/main` для типов бекенда
- **Слой заводится тогда, когда для него есть код** — пустые директории впрок не создаются (сейчас реально существуют только `app`, `pages` и `shared`)
- **Внутри слайса — сегменты** `ui/` (компоненты) и `model/` (состояние, схемы, обёртки над `window.api`); прочие сегменты FSD добавляются по мере появления кода
- **Публичный API слайса — barrel `index.ts`**; импорт мимо него в чужой слайс — нарушение границы
- **Компонент не обращается к `window.api` напрямую** — только через функцию из `model/`
- **Схемы и типы, определённые на бекенде, не дублируются** — импортируются через `@/main/*`
- **Серверного стейта и глобального стора нет** — локальное состояние компонентов; введение TanStack Query, Zustand или аналога требует отдельного ADR

**Общее для обеих сторон:**

- **Единица переиспользования отдаёт наружу явный публичный API** — barrel-файл модуля на бекенде и слайса на фронтенде; всё остальное считается внутренней реализацией
- **Граница между процессами — типизированный контракт-значение**, а не поток исключений; владелец контракта — бекенд


## Последствия

- Нарезка «модуль → слои» на бекенде даёт высокое зацепление внутри доменной области: всё, что относится к `auth`, лежит рядом, а добавление модуля не размазывается по трём деревьям слоёв. Плата — три почти пустые директории у каждого нового модуля и соблазн сложить в `shared/` то, что на деле принадлежит конкретному модулю.
- IPC-контракт в `domain/contracts/` исключает расхождение типов между процессами: renderer компилируется против того же типа, который возвращает контроллер, и поломка контракта видна на `yarn typecheck`, а не в рантайме. Плата — фронтенд импортирует код бекенда напрямую (`@/main/*`), то есть слои связаны сильнее, чем при отдельном пакете общих типов; правило «только типы и Zod-схемы» держится дисциплиной и ревью, а не сборкой.
- Отказ-как-значение делает все ветви обработки ошибок видимыми в типах и заставляет UI явно разбирать `error.type` — забыть про ошибку молча нельзя. Плата — на каждый новый различимый снаружи случай отказа нужен доменный класс ошибки, член union'а и ветка в UI; для тривиальных операций это заметный boilerplate.
- Ручной DI в одной точке делает граф зависимостей читаемым без магии и не добавляет зависимостей в проект, но `src/main/index.ts` будет линейно расти с числом модулей и рано или поздно потребует разбиения на функции сборки по модулям.
- Value objects со `safeParse` и ООП-стиль дают предсказуемую форму кода, которую агент воспроизводит по образцу соседнего модуля, но делают простые случаи многословнее функционального эквивалента.
- Требование заводить слой FSD только под реальный код бережёт от каркаса из пустых директорий, но означает, что структура фронтенда сейчас не совпадает с полной схемой FSD — читая только руководство, легко ожидать `widgets/` и `features/`, которых пока нет.
- Запрет на серверный стейт по умолчанию не даст протащить тяжёлую зависимость в рамках рядовой фичи, но страницы **Задачи** и **Календарь** с пагинацией почти наверняка упрутся в это ограничение — ADR о кэшировании данных ожидается как следующее значимое решение.
- Конвенции зафиксированы в двух местах с разным назначением: этот ADR хранит решение и его причины, руководства — актуальные правила. При изменении конвенции правится руководство, а ADR либо остаётся историческим свидетельством, либо помечается `Устарело` и заменяется новым — синхронно править оба файла не требуется, но и молча расходиться по смыслу они не должны.
