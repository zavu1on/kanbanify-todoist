# Architecture Decision Records

**ADR (Architecture Decision Record)** — короткий документ, фиксирующий *значимое* архитектурное или техническое решение: контекст, что было выбрано, почему и какие у этого последствия.

Паттерн позволяет сохранить историю решений прямо в репозитории, чтобы любой участник команды (или будущий разработчик) мог понять, *почему* система устроена именно так.


## Когда создавать ADR

Создавай ADR, если решение:

- неочевидно — есть альтернативы с реальными компромиссами
- трудно обратимо — смена подхода потребует значительных усилий
- системно значимо — влияет на структуру системы, модель данных или поведение нескольких компонентов


## Процесс

1. Создай файл в `docs/decisions/` с именем `NN-название-решения.md`, где `NN` — следующий порядковый номер
2. Заполни файл по шаблону ниже
3. Выставь статус `Предложено`, обсуди с командой
4. После принятия смени статус на `Принято`
5. Если решение устарело или отменено — смени статус на `Устарело` или `Отклонено` и укажи причину в разделе **Последствия**


## Шаблон

```markdown
# NN. Название решения

**Дата:** YYYY-MM-DD
**Автор:** Имя
**Статус:** Предложено | Принято | Отклонено | Устарело
**Связанные решения:** [NN-название.md](NN-название.md)


## Контекст

Описание ситуации и проблемы, которую нужно решить. Почему это решение вообще потребовалось?


## Решение

Что именно было решено. Краткая формулировка выбора.


## Последствия

Что вытекает из этого решения: плюсы, минусы, ограничения, на что повлияет.
```
