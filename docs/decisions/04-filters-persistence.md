# 04. Локальное хранилище конфигурации фильтров

**Дата:** 2026-09-01
**Автор:** mikhail
**Статус:** Принято
**Связанные решения:** [01-tech-stack.md](01-tech-stack.md), [02-architecture.md](02-architecture.md)


## Контекст

Фича «Фильтры» добавляет пользовательские сохранённые Todoist filter query — отдельные вкладки в сайдбаре, каждая со своим `title`, цветом и query-строкой. Это не Todoist-сущность: запрос задач по query уже возможен через существующий `ITaskGateway.listTasksByFilter`, но сама конфигурация фильтра (какие вкладки завёл пользователь) нигде на стороне Todoist не хранится и должна персистироваться локально.

До этой фичи в проекте не было ни одной настоящей локальной базы данных — единственный прецедент локальной персистентности, `SafeStorageTokenStore` (`src/main/auth/infrastructure/SafeStorageTokenStore.ts`), хранит один плоский зашифрованный файл (Todoist access token), а не набор записей с CRUD. Нужно решить, чем и как хранить произвольное число строк `{id, title, color, query}`.


## Решение

Хранить фильтры в **sqlite** через **`better-sqlite3`**, файл `filters.db` в `app.getPath("userData")`, одна таблица `filters`, схема создаётся один раз через `CREATE TABLE IF NOT EXISTS` (без миграционного фреймворка). `id` — `INTEGER PRIMARY KEY AUTOINCREMENT`: порядок вкладок в сайдбаре — порядок создания, отдельного изменения порядка (drag-reorder) не предусмотрено, поэтому колонка сортировки не нужна — `AUTOINCREMENT` уже гарантирует, что `SELECT ... ORDER BY id ASC` возвращает строки в порядке создания.

Рассмотренная альтернатива — `node:sqlite` (появился в Node core, экспериментальный с версии ~22.5). Отклонена как решение по умолчанию: версия Node, зашитая в используемый Electron `^43.2.0`, не была подтверждена (проверка через живой Electron зависла в headless-окружении разработки), и завязывать единственный слой персистентности приложения на экспериментальный core-модуль с неподтверждённым нижним порогом версии — неоправданный риск. `better-sqlite3` — де-факто стандартный выбор для Electron-приложений: синхронный API (не нужно оборачивать use-case'ы в промисы ради консистентности с остальными портами — асинхронность на уровне порта сохраняется за счёт сигнатур `IFilterStore`, а не самой библиотеки), широкое использование, предсказуемое поведение под нагрузкой уровня «несколько десятков строк».


## Последствия

- **Новая нативная зависимость.** `better-sqlite3` компилируется под конкретный ABI Node/Electron — при установке или смене версии Electron требуется пересборка.
- **`electron-builder` уже покрывает паковку** (`dist:win`) — он ребилдит нативные зависимости перед упаковкой автоматически, конфигурация не меняется.
- **Локальная разработка (`yarn dev`/`yarn start`) не покрыта автоматически** — эти команды запускают Electron напрямую поверх `node_modules`, где `better-sqlite3` уже должен быть собран под ABI Electron. Добавляется `@electron/rebuild` в `devDependencies` и скрипт `"postinstall": "electron-rebuild -f -w better-sqlite3"` в `package.json`, чтобы `yarn install` сразу оставлял корректно собранный биндинг.
- **Одна таблица, без миграций.** `CREATE TABLE IF NOT EXISTS` — достаточный минимум для одной сущности без версионируемой схемы. Если появится вторая таблица или потребуется менять схему существующих строк, этого будет недостаточно — тогда стоит завести полноценный migration-шаг (например, `drizzle-kit`) отдельным решением.
- **Файл БД не синхронизируется и не шифруется** — фильтры не содержат секретов (в отличие от access token), поэтому шифрование через `safeStorage`, как у `SafeStorageTokenStore`, не требуется.
