# 01. Технологический стек и архитектура

**Дата:** 2026-08-02
**Автор:** mikhail
**Статус:** Принято

## Контекст

Проекту нужен desktop-клиент к Todoist API с UI поверх встроенных тегов (см. [`../SPECIFICATION.md`](../SPECIFICATION.md)) — включая kanban-доску с drag-and-drop. Личный Todoist Access Token должен храниться и использоваться так, чтобы не быть доступным напрямую из UI-слоя (см. раздел «Авторизация» в [`../SPECIFICATION.md`](../SPECIFICATION.md)).

Это требует решений на нескольких независимых уровнях: платформа приложения (desktop-обёртка), UI-библиотека, способ реализации drag-and-drop для канбан-доски, связь между процессом с доступом к токену и процессом отрисовки UI, а также внутренняя организация кода на обеих сторонах. Рассматривались альтернативы — например, Tauri вместо Electron (меньше веса рантайма, но Rust-бекенд вместо TS и менее зрелая экосистема) и веб-приложение без десктопной обёртки (проще деплой, но нет `safeStorage` и изолированного main-процесса для токена).


## Решение

**Бекенд** (Electron main-процесс):

- **Electron** — платформа desktop-приложения
- **`@doist/todoist-sdk`** — официальный TS SDK для работы с Todoist API
- Архитектура — **чистая архитектура** (Clean Architecture)

**Фронтенд** (Electron renderer-процесс):

- **React** — UI-библиотека
- **React Router** — маршрутизация между экранами
- **Mantine UI** — компонентная библиотека
- **dnd-kit** — drag-and-drop для канбан-доски
- Архитектура — **FSD** (Feature-Sliced Design)

**Связь бекенда и фронтенда** — Electron **IPC**: renderer не имеет прямого доступа к Todoist-токену и ходит к Todoist API только через IPC-вызовы к main-процессу.


## Последствия

- Токен хранится и используется исключительно в main-процессе (через `safeStorage`), renderer физически не может получить к нему доступ в открытом виде — снижает риск утечки токена через уязвимости в UI-слое (например, через сторонние React-компоненты).
- Electron даёт кросс-платформенность (Windows/macOS/Linux) из коробки, но приложение наследует typичный для Electron вес рантайма (bundled Chromium + Node.js) по сравнению с нативными или Tauri-based альтернативами.
- Официальный `@doist/todoist-sdk` снимает необходимость самостоятельно поддерживать HTTP-клиент к Todoist API, но привязывает бекенд к темпу обновлений и ограничениям самого SDK.
- Чистая архитектура на бекенде изолирует доменную логику (kanban-статусы, доменную модель задач) от Electron- и Todoist SDK-специфичных деталей, упрощая тестирование и потенциальную замену SDK, но требует больше boilerplate-слоёв (use cases, adapters, gateways) уже на старте проекта.
- FSD на фронтенде задаёт единый способ организации фич (слои, сегменты, публичные API слайсов) — снижает произвол в структуре по мере роста числа экранов, но требует дисциплины в соблюдении границ слоёв и добавляет когнитивную нагрузку для разработчика, незнакомого с паттерном.
- Каждое изменение состояния канбан-доски (drag-and-drop через dnd-kit) должно транслироваться в IPC-вызов к main-процессу и обратно в Todoist API — синхронный на вид UI-жест становится асинхронной операцией с сетевой задержкой, что нужно учитывать в UX (оптимистичные обновления, откат при ошибке).
- Выбор React Router и Mantine UI фиксирует конкретные API этих библиотек в компонентах фич — миграция на другой роутер или UI-kit потребует переписывания значительной части фронтенда.
